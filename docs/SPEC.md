**Техническое задание: SpaceOps**

**Цифровая платформа управления офисами и коворкингами**

**1. Цель проекта**

Разработать веб-приложение, в котором сотрудники бронируют переговорные и рабочие места, а диспетчер управляет доступностью помещений, оборудованием и обращениями.

Приложение должно демонстрировать:

- разработку интерактивного интерфейса;
- проектирование API и реляционной базы данных;
- разграничение прав пользователей;
- работу с транзакциями и конкурентными запросами;
- тестирование бизнес-логики;
- развёртывание работающего продукта.

**2. Границы первой версии**

Первая версия обслуживает один коворкинг с двумя этажами.

Демонстрационные данные: 8 переговорных, 30 рабочих мест, оборудование и несколько пользователей разных ролей.

В обязательную версию входят:

- авторизация;
- интерактивный план этажей;
- бронирование переговорных и рабочих мест;
- каталог оборудования;
- обращения о неисправностях;
- блокировка помещений;
- подбор и подтверждение переноса бронирований;
- уведомления внутри приложения;
- простая аналитика.

Редактор планов, оплата, интеграция с календарями, датчики присутствия, повторяющиеся бронирования и отправка email остаются за пределами первой версии.

**3. Роли и права**

| Действие | Сотрудник | Диспетчер | Администратор |
|---|---|---|---|
| Просматривать план и доступность | Да | Да | Да |
| Создавать бронирования | Для себя | Для себя | Для себя |
| Отменять бронирования | Свои | Любые | Любые |
| Создавать обращения | Да | Да | Да |
| Просматривать обращения | Свои | Все | Все |
| Назначать исполнителя и менять статус обращения | Нет | Да | Да |
| Блокировать помещения и предлагать перенос | Нет | Да | Да |
| Подтверждать перенос собственной встречи | Да | Да | Да |
| Управлять помещениями и оборудованием | Нет | Да | Да |
| Изменять роли пользователей | Нет | Нет | Да |

Права проверяются на сервере. Скрытая кнопка в интерфейсе не является защитой.

Диспетчер выступает исполнителем обращений; отдельная роль техника в первой версии не нужна.

Redis, микросервисы и отдельный брокер сообщений для первой версии не требуются.

**5. Архитектура**

Один репозиторий:

- `apps/web` — клиентское приложение;
- `apps/api` — сервер;
- `docs` — схема данных, описание архитектуры и сценарий демонстрации;
- `infra` — настройки запуска.

Бэкенд реализуется как модульный монолит:

- Auth — вход, выход и сессии;
- Users — пользователи и роли;
- Spaces — этажи, помещения и рабочие места;
- Bookings — бронирования;
- Equipment — оборудование;
- Tickets — обращения;
- Relocations — предложения переноса;
- Notifications — уведомления;
- Analytics — агрегированные показатели;
- Audit — история значимых изменений.

Клиент работает с сервером через REST API с префиксом `/api/v1`.

Для первой версии обновление плана и уведомлений выполняется опросом сервера каждые 30 секунд, а после действий пользователя — сразу. Настоящие обновления через SSE можно добавить после завершения основного сценария.

**6. Фронтенд и экраны**

**6.1. Общий интерфейс**

На компьютере:

- слева — меню разделов;
- сверху — название площадки, уведомления и профиль;
- в центре — содержимое выбранного раздела;
- справа — панель подробностей выбранного объекта.

Основные разделы: «План», «Бронирования», «Обращения», «Оборудование», «Аналитика», «Настройки».

Визуальный стиль: светлый фон, спокойные нейтральные поверхности, один основной акцентный цвет, читаемая типографика.

Для каждой страницы предусматриваются состояния загрузки, ошибки и отсутствия данных.

**6.2. Вход**

Поля: email и пароль.

После входа пользователь попадает на план этажа. Ошибка авторизации показывается без раскрытия того, существует ли введённый email.

Самостоятельная регистрация не входит в первую версию. Демонстрационные пользователи создаются начальным заполнением базы.

**6.3. Интерактивный план**

Основной экран приложения.

Элементы:

- переключатель этажа;
- режим «Сейчас»;
- выбор даты и временного интервала;
- фильтры по типу пространства, вместимости и оборудованию;
- легенда состояний;
- увеличение, уменьшение и сброс масштаба;
- переключение между планом и списком.

Комнаты представлены SVG-полигонами, рабочие места — небольшими отдельными объектами. Геометрия загружается из заранее подготовленных данных; рисовать план внутри приложения не требуется.

Состояния:

- зелёный — доступно;
- синий — есть бронирование;
- серый — временно недоступно;
- жёлтый значок — есть открытое обращение.

Обращение само по себе не блокирует комнату.

Цвет дополняется подписью или значком. В режиме выбранного интервала любое пересечение с активным бронированием означает, что пространство недоступно для бронирования на весь этот интервал.

По нажатию открывается карточка:

- название и тип;
- этаж и вместимость;
- оборудование и его состояние;
- доступность на выбранное время;
- расписание на выбранный день;
- действия «Забронировать» и «Сообщить о проблеме»;
- для диспетчера — «Ограничить доступность».

В режиме «Сейчас» приложение показывает состояние по расписанию. Фактическое присутствие людей первая версия не определяет.

**6.4. Бронирования**

Два представления:

- календарь на день или неделю;
- список собственных бронирований.

Форма бронирования:

- пространство;
- название встречи;
- дата, начало и окончание;
- количество участников;
- необходимое оборудование;
- комментарий.

Для рабочего места количество участников равно одному.

Перед отправкой показывается краткое подтверждение. При конфликте сервер возвращает понятную ошибку, интерфейс обновляет доступность и сохраняет введённые данные.

Перенос времени выполняется через форму редактирования. Перетаскивание событий — дополнительная функция после завершения MVP.

**6.5. Обращения**

Сотрудник видит свои обращения, диспетчер — общую очередь.

Поля обращения:

- тема и описание;
- помещение;
- конкретное оборудование, если применимо;
- категория;
- приоритет;
- автор;
- исполнитель;
- статус;
- дата создания.

Статусы: «Новое» → «В работе» → «Решено» → «Закрыто».

Закрытое обращение диспетчер может вернуть в работу с обязательным комментарием.

Карточка содержит комментарии и историю изменений. Фотографии можно добавить отдельным этапом; базовый сценарий должен работать без загрузки файлов.

**6.6. Рабочий экран диспетчера**

Показывает:

- новые обращения;
- помещения с ограниченной доступностью;
- бронирования, затронутые блокировками;
- предложения переноса, ожидающие ответа.

Из каждой записи можно перейти к соответствующей комнате, заявке или бронированию.

**6.7. Оборудование**

Таблица с поиском и фильтрами:

- название;
- инвентарный номер;
- категория;
- расположение;
- состояние: исправно, неисправно, в ремонте.

Оборудование не бронируется отдельно. Оно учитывается при выборе комнаты и подборе замены.

**6.8. Аналитика**

Период: выбранная неделя или месяц.

Показатели:

- количество активных и отменённых бронирований;
- загрузка переговорных;
- количество открытых обращений;
- среднее время от создания до решения обращения.

Загрузка рассчитывается как отношение забронированных минут к доступным рабочим минутам. Периоды блокировок исключаются из доступного времени; если доступное время равно нулю, показывается «Нет данных».

В первой версии это аналитика бронирований, а не фактической посещаемости.

**6.9. Мобильная версия**

На небольшом экране по умолчанию открывается список помещений, план доступен отдельно.

Обязательные мобильные сценарии:

- найти помещение;
- забронировать;
- посмотреть и отменить своё бронирование;
- создать обращение;
- принять или отклонить перенос.

**7. Бизнес-правила бронирования**

- Начало должно быть раньше окончания.
- Бронировать прошедшее время нельзя.
- Шаг выбора времени — 15 минут.
- Минимальная продолжительность — 15 минут, максимальная — 8 часов.
- Бронирование должно полностью попадать в рабочее время площадки.
- Рабочее время демонстрационной площадки: ежедневно с 08:00 до 22:00.
- Вместимость должна соответствовать количеству участников.
- Требуемое оборудование должно быть исправно.
- Активные бронирования одного пространства не могут пересекаться.
- Блокировка запрещает новые бронирования на пересекающееся время.
- Отменённые бронирования сохраняются в истории.

Интервалы считаются полуоткрытыми: `[начало, окончание)`. Встречи 10:00–11:00 и 11:00–12:00 совместимы.

В базе время хранится как `timestamptz`; рабочее расписание и отображение определяются часовым поясом площадки.

**Защита от двойного бронирования**

Проверка выполняется на сервере в транзакции.

Для активных бронирований применяется ограничение PostgreSQL, запрещающее пересечение временных диапазонов одного пространства.

Дополнительно создание бронирования и установка блокировки используют блокировку одной и той же строки пространства в транзакции. После получения блокировки сервер повторно проверяет условия. Так закрытие помещения и новое бронирование не могут пройти независимо друг от друга.

При двух одновременных запросах на одно время:

- один получает подтверждение;
- второй получает `409 Conflict`;
- в базе остаётся одно активное бронирование.

**8. Блокировка помещения и перенос**

1. Диспетчер выбирает помещение, причину и период блокировки.
2. Сервер сохраняет блокировку и находит затронутые активные бронирования.
3. Новые бронирования на этот период запрещаются.
4. Затронутые встречи получают признак «Требуется перенос».
5. Сервер подбирает альтернативы.
6. Диспетчер отправляет владельцу встречи предложение.
7. Владелец принимает или отклоняет его.
8. При принятии сервер повторно проверяет доступность и атомарно меняет помещение бронирования.
9. Участники процесса получают уведомления внутри приложения.

Критерии альтернатив:

- тот же временной интервал;
- тот же тип пространства;
- достаточная вместимость;
- наличие необходимого исправного оборудования;
- отсутствие бронирований и блокировок.

Сначала показываются варианты на том же этаже, затем — на другом.

Предложение не резервирует альтернативную комнату. Если к моменту подтверждения она занята, перенос не выполняется, пользователь получает сообщение, а диспетчер подбирает новый вариант.

При отклонении предложения исходная запись сохраняется с отметкой проблемы. Она не означает, что закрытой комнатой можно пользоваться. Диспетчер должен предложить другой вариант или отменить встречу.

Если альтернатив нет, приложение сообщает об этом прямо.

После ремонта диспетчер снимает блокировку. Уже перенесённые встречи автоматически назад не возвращаются.

**9. Основные сущности данных**

| Сущность | Основные поля |
|---|---|
| User | id, имя, email, хеш пароля, роль |
| Session | пользователь, хеш токена, срок действия |
| Site | название, часовой пояс, рабочие часы |
| Floor | площадка, номер, название |
| Space | этаж, тип, название, вместимость, SVG-геометрия, архивность |
| Equipment | помещение, категория, название, инвентарный номер, состояние |
| Booking | пространство, автор, название, начало, окончание, число участников, статус |
| BookingRequirement | бронирование, категория требуемого оборудования |
| AvailabilityBlock | пространство, начало, окончание, причина, автор |
| Ticket | помещение, оборудование, автор, исполнитель, приоритет, статус, описание |
| TicketComment | обращение, автор, текст, дата |
| RelocationProposal | бронирование, предлагаемое пространство, статус, автор |
| Notification | получатель, тип, объект, дата прочтения |
| AuditLog | инициатор, действие, объект, изменения, время |

Помещения с историей архивируются вместо удаления. Операции над бронированием используют номер версии записи, чтобы устаревшее предложение не изменило уже отредактированную встречу.

**10. API**

Основные маршруты:

| Метод и маршрут | Назначение |
|---|---|
| `POST /auth/login` | Вход |
| `POST /auth/logout` | Выход |
| `GET /auth/me` | Текущий пользователь |
| `GET /floors` | Этажи |
| `GET /floors/:id/plan` | Геометрия и состояния пространств |
| `GET /spaces` | Поиск помещений и рабочих мест |
| `GET /spaces/:id` | Карточка пространства |
| `GET /bookings` | Бронирования за период |
| `POST /bookings` | Создание |
| `PATCH /bookings/:id` | Изменение |
| `POST /bookings/:id/cancel` | Отмена |
| `POST /spaces/:id/blocks` | Создание ограничения |
| `POST /blocks/:id/release` | Снятие ограничения |
| `GET /blocks/:id/affected-bookings` | Затронутые встречи |
| `GET /bookings/:id/alternatives` | Варианты переноса |
| `POST /bookings/:id/relocation-proposals` | Предложение переноса |
| `POST /relocation-proposals/:id/accept` | Подтверждение |
| `POST /relocation-proposals/:id/reject` | Отказ |
| `GET /equipment` | Список оборудования |
| `GET /tickets` | Список обращений |
| `POST /tickets` | Создание обращения |
| `PATCH /tickets/:id` | Изменение статуса и исполнителя |
| `POST /tickets/:id/comments` | Комментарий |
| `GET /notifications` | Уведомления |
| `GET /analytics/overview` | Сводные показатели |

Списки поддерживают пагинацию и допустимые фильтры. Сервер ограничивает максимальный диапазон дат для тяжёлых запросов.

Ошибки имеют единый формат: `code`, `message`, `details`.

**11. Авторизация и защита данных**

Используются серверные сессии. Случайный токен передаётся в `HttpOnly` cookie, в базе хранится его хеш.

Требования:

- хеширование паролей Argon2id;
- `Secure` cookie в опубликованной версии;
- ограничение частоты попыток входа;
- защита изменяющих запросов от CSRF;
- серверная проверка входных данных;
- проверка роли и владельца объекта;
- секреты только через переменные окружения;
- отсутствие паролей и токенов в логах.

Клиент и API публикуются на одном домене.

Другие сотрудники видят занятость пространства, но не приватное описание чужой встречи. Диспетчер получает детали, необходимые для перепланирования.

**12. Проверки и критерии приёмки**

Проект готов, если:

1. Приложение запускается по инструкции из README.
2. Миграции и начальное заполнение создают рабочую демонстрационную площадку.
3. Все три роли могут войти и получают соответствующие права.
4. Выбор этажа и времени меняет состояния на плане.
5. Созданное бронирование отображается в календаре и карточке комнаты.
6. Два одновременных запроса не создают пересекающиеся бронирования.
7. Сотрудник не может изменить чужую запись подстановкой ID в API.
8. Блокировка помещения показывает затронутые встречи.
9. Предложение переноса требует подтверждения владельца.
10. Занятая после отправки предложения альтернатива не приводит к двойному бронированию.
11. Отмена исходной встречи делает её предложение переноса недействительным.
12. Изменения доступности и переносы сохраняются в истории.
13. Основной сценарий работает на мобильном экране.
14. Проверки типов, тесты и сборка проходят в CI.

Особенно важны интеграционные тесты с настоящей PostgreSQL: конкурентное бронирование, одновременная блокировка и бронирование, подтверждение устаревшего предложения.

Сквозной тест должен проходить путь: бронирование → обращение → блокировка → предложение → подтверждение → новое помещение.

**13. Этапы реализации**

| Этап | Результат |
|---|---|
| 1. Основа | Репозиторий, окружение, схема базы, миграции, тестовые данные |
| 2. Доступ | Авторизация, сессии, роли и общий каркас интерфейса |
| 3. Пространства | План двух этажей, фильтры и карточки |
| 4. Бронирования | Создание, изменение, отмена, календарь и защита от конфликтов |
| 5. Эксплуатация | Оборудование, обращения и история действий |
| 6. Перепланирование | Блокировки, поиск альтернатив и подтверждение переноса |
| 7. Завершение | Уведомления, аналитика, мобильные сценарии, тесты и публикация |

Ориентир для одного разработчика, знакомого со стеком: 6–8 недель при занятости около 15–20 часов в неделю. Это оценка; изучение технологий с нуля потребует дополнительного времени.

Если срок ограничен, сначала сокращаются аналитика и визуальные улучшения. Защита от конфликтов, права и основной сценарий переноса остаются обязательными.

**Сценарий демонстрации**

Сотрудник выбирает переговорную на плане и бронирует её. Затем создаёт обращение о неисправном проекторе. Диспетчер открывает обращение, блокирует комнату и видит затронутую встречу. Система предлагает подходящую переговорную. После подтверждения сотрудником встреча переносится, а изменение появляется в истории.

Отдельно показывается конкурентный запрос: из двух попыток забронировать одну комнату на одинаковое время успешна только одна.

**15. Возможное развитие**

После завершения первой версии:

- повторяющиеся бронирования с исключениями;

- фотографии в обращениях;
- напоминания;
- подтверждение присутствия и учёт неявок;
- перенос событий в календаре мышью;
- редактор плана;
- несколько площадок;
- интеграция с внешними календарями.
