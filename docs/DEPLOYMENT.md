# Развёртывание

Проект предназначен для одного сервера с Docker Compose, PostgreSQL и nginx. Для production нужен свой домен и HTTPS-терминация, например Caddy либо nginx с сертификатом. Автоматическая публикация в сторонний аккаунт не выполняется.

1. Скопировать репозиторий на сервер. Создать `.env` из `.env.example`.
2. Установить сильный `POSTGRES_PASSWORD`, уникальный `DEMO_PASSWORD` длиной от 12 символов. Для простоты Compose URL используйте URL-safe символы в пароле PostgreSQL либо соберите connection URL с percent encoding вручную.
3. Установить `PUBLIC_URL=https://spaceops.example.com` **без завершающего слеша**, `COOKIE_SECURE=true`.
4. Настроить HTTPS-прокси на `127.0.0.1:8080`; приложение и `/api` должны оставаться на одном origin. API и БД не открывать в интернет. Маппинг PostgreSQL на 127.0.0.1 можно убрать, если локальный доступ не нужен.
5. `docker compose --env-file .env -f infra/compose.yaml up --build -d`.
6. Проверить `/api/v1/health`, войти каждой ролью, пройти сценарий из DEMO.md. В production ограничить доступ к Swagger на уровне прокси, если документация не должна быть публичной.
7. Настроить резервное копирование тома PostgreSQL и проверить восстановление. Обновления выполнять с резервной копией и планом отката, поскольку миграции могут менять схему.

Пример логической резервной копии (файл вне Git):

```bash
docker compose --env-file .env -f infra/compose.yaml exec -T db \
  pg_dump -U spaceops -d spaceops > spaceops-backup.sql
```

Подставьте свои POSTGRES_USER/POSTGRES_DB. Не коммитьте резервные копии с данными пользователей. `docker compose down` сохраняет том; `down -v` удаляет его вместе с данными.

API использует лимит входа в памяти одного процесса. Для нескольких экземпляров потребуется общий лимитер и согласованная настройка доверенного прокси. Распределённые бронирования уже защищены транзакциями и ограничениями PostgreSQL.
